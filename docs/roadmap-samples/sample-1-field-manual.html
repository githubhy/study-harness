Harness Dissection Manual

Build a transferable model of agent harnesses as a category by dissecting DeepSeek Harness — then test whether that model explains a harness it was never derived from.

specimen deepseek-harness pinned 47f9438 · 2026-08-13 packages 49, all covered threads 15 · 12 source-only transfer test Claude Code transcripts completion none — surprise budget
§ 1

The subject

A language model is a function from text to text. It cannot read a file, run a command, or remember anything. A harness is the program wrapped around it that supplies all three. Everything else — compaction, permissions, plugins, sandboxing, delegation — is a refinement of one of these five steps.

§ 2

Method

Three claims the whole study rests on. If any is wrong, the plan below is the wrong plan.

You can't read what you can't name
Writing a harness first supplies the vocabulary that makes a real one legible. Reading agent-loop cold teaches nothing; reading it after writing a loop teaches everything.
The wire beats the source
Prompt assembly is scattered across dozens of files. The bytes sent to the API are single, literal ground truth. When a reading and a capture disagree, the capture wins.
A vocabulary must transfer
Concepts that only explain their own specimen are worthless. The study succeeds if ideas derived from dsh explain Claude Code — and fails if they don't.
§ 3

Standing orders

Six rules that hold in every phase and every thread. Read them once; they are assumed everywhere below.

The canonical task
Used verbatim for every harness so captures stay comparable — your toy, dsh, and Claude Code all get the same prompt: “Create a file called fizzbuzz.js that prints FizzBuzz for 1..20, then run it with node and show me the output.” It forces read, write, and execute in one run.
The surprise budget
There is no completion criterion. Abandon a thread after two consecutive findings that don't surprise you, and file it as a needs-triage issue. A dry thread is a result, not a failure.
The wire wins
When your reading of the source and the captured bytes disagree, the reading is wrong. Fix the note, not the capture.
Never commit captures
captures/ is gitignored and the proxy redacts auth headers before writing. A leaked key in a capture is the one unrecoverable mistake here.
Analyse, don't dump
dsh's prompt ships in a public MIT repo and can be quoted freely. Claude Code transcripts are personal working history — cite structure, counts, and tool names only. This repo is public.
Glossary as you go
When a thread sharpens a term, it lands in CONTEXT.md that session — never batched to the end. Terms get re-sorted in Phase 4, and being wrong early is data.

1
Write a harness from scratch the control
blocked by Phase 0 · about an hour · produces the question list driving Phase 2

~45 lines against the DeepSeek API: a message list, two tools, a loop, a step cap. The only harness whose every byte you can account for — and therefore the reference against which dsh's captures are read.

The whole thing, in shape

messages = [system, user]
for step in 1..10:
    msg = POST /chat/completions {model, messages, tools}
    messages.push(msg)
    if not msg.tool_calls: print(msg.content); break
    for call in msg.tool_calls:
        result = impls[call.name](call.args)
        messages.push({role:'tool', tool_call_id, content: result.slice(0,4000)})

Then break it deliberately

  • Blow the truncation: ask it to read package-lock.json and list the dependencies.
  • Blow the step cap: twelve sorting algorithms, each run and compared.
  • Expose the missing permission layer: ask it to delete every .tmp under /tmp. The alarm you feel is packages/guard's entire reason to exist.

Deliverables

experiments/minimal-harness/harness.mjs, a capture of your own harness through the proxy, and notes/01-what-my-harness-lacks.md — the table that becomes §5. First real CONTEXT.md terms land here: loop, turn, step, tool call, tool result, context window.

3
Exam · one tool, two harnesses gated on Thread D
gated on Thread D · both round trips must close

The same trivial tool built twice — as a dsh plugin and as an MCP server for Claude Code. The diff between the two integrations is the finding.

Two things must be true, per harness

The tool was offered, and the model called it. Proving only the first is the classic false pass — it shows registration worked while the loop never closed around it.

# offered (dsh, from the capture)
jq -r 'select(.dir=="request") | .body.tools[]? | .function.name' \
  captures/session-plugin.jsonl | sort -u | rg hello_study

# called (either harness — grep the marker)
rg -c 'STUDY-MARKER-7f3a' captures/session-plugin.jsonl

Why this is the category exam

What both harnesses demand of a tool is essential to the category. What only one demands is incidental to its implementation. That intersection is the real model of “a tool” — and MCP versus a Cordis plugin is itself an answer to Thread E's question about where an extension boundary belongs.

4
Transfer test must be last
blocked by Phase 2 · last by design — reading earlier makes the test circular

Commit predictions before opening the Claude Code transcripts already on disk, then score them. Sort every glossary term into universal, dsh-specific, or missing.

Predict first, and commit the prediction

From the dsh-derived model alone, write down which tools you expect, how results appear serialized, what stop reasons exist, how permissions are gated. A prediction made after looking tests nothing — so it goes in a commit before the first jq runs.

Three buckets, and two of them are the output

  • Universal — explains both harnesses. Stays canonical in CONTEXT.md.
  • dsh-specific — an implementation detail you mistook for a category concept.
  • Missing — Claude Code does something your vocabulary can't name. thinking blocks, hooks, and sidechains are the likely candidates.

Buckets two and three are what the study actually produced. Bucket one is just what survived.

EPlugin architecture
Packages
core/scopebootextensionsbundle
source only

Where should a harness's extension boundary sit, and what does “everything is a plugin” make hard?

RAISED BY no plugins, no extension points

cat packages/core/README.md AGENTS.md CLAUDE.md packages/AGENTS.md
rg -n 'ctx\.(plugin|on|set|inject)' packages/core --type ts

Learn Cordis first or this thread fails. It's dependency injection plus an event bus — nothing calls anything directly, so grep-based tracing finds nothing and the codebase reads as indirection with no call graph. There's a paper behind it: A Programming Paradigm for Spatiotemporal Composability.

The repo's own AGENTS.md and CLAUDE.md are written to orient agents working in it, which makes them the best human onboarding docs too — usually fresher than docs/.

KThe host boundary
Packages
hostclientinteractionapps/
source only

Where does the harness end and the user interface begin? Could you drive it with no UI at all?

RAISED BY printing to stdout

Your toy printed to stdout. dsh serves a web UI on 127.0.0.1:3080, so it has drawn a boundary somewhere — and where that line sits determines whether the harness can be embedded, scripted, or driven headlessly.

Determine the transport between core and UI (HTTP, WebSocket, JSON-RPC, in-process?), and whether streaming reaches the UI as the raw model stream or as re-emitted domain events. Then answer the real question: what is the minimum surface a headless embedder needs?

LProvider abstraction
Packages

source only

What does it take to be model-agnostic, and where does the abstraction leak?

RAISED BY hard-coding one provider's wire format

Read the shared llm interface, then both implementations behind it. What sits in the interface that only one provider actually needs? That is where the abstraction leaks.

Then llm-retry: which failures are retried, with what backoff, and is a retried call visible to the loop or hidden beneath it? A hidden retry changes what “one step” means.

RAISED BY no way to observe or interrupt it

OAgent self-management
Packages
todoskillworkflow
source onlyCC comparison

What tools does a harness give the model for managing its own process, rather than the user's task?

RAISED BY the model being unable to track its own plan

A category of tool your toy has no concept of: the model tracking its own plan, loading its own instructions, running predefined procedures. Every one has a direct Claude Code analogue, making this the densest comparison surface in the study.

  • todo — is the list context (re-sent every turn, costing tokens) or external state (stored, referenced)? That choice is the whole design question.
  • skill — does the model request one by name, or does the harness inject it on a match?
  • workflow — what distinguishes it from a plan (Thread F) and from a skill? If the code doesn't make that clear, the ambiguity is the finding.
